# JOURNEY：我们为什么这么走

这份是写给人看的。照着搭请看 [BUILD.md](../BUILD.md)，那份是给 AI 的开工说明。

这里记的是：每一处为什么选了现在这条路，在哪儿卡住过，怎么过去的。这些选择很多取决于我们手上已经有什么，不一定适合你。

---

## 几个关键选择

| 选择 | 为什么 |
|---|---|
| 脑子用 **Claude Code 会话本身**，每轮 fork 一份来回答 | 我们要的不是「一个 Claude」，而是天天在用的那个窗口里的同一个，带着正在聊的、正在做的事。代价是每轮约 14 秒，我们接受。 |
| **不给脑子任何工具** | 安全。机器人的麦克风是外放的，谁站在旁边说话它都听。要是能调工具，路过的人一句话就能让 Mac 执行命令。代价是它当轮看不到自己拍的照片，要看得回 Claude Code 窗口里说。详见 [ARCHITECTURE](ARCHITECTURE.md#为什么不给它手)。 |
| 经 **VPS + ssh 反向隧道** 连回家 | 我们本来就有一台付了费的 VPS，一开始接 Claude 时就在用它。机器人是 ESP32，装不了组网客户端；用反向隧道，家里不用开任何端口，Mac 主动连出去就行。 |
| 嗓音用 **MiniMax** 云端克隆 | 我们订了 MiniMax 的套餐。本地克隆试过，太慢（见下）。 |
| 语音识别跑在 **Mac 本机**（mlx-whisper） | Mac 本来就开着当脑子，本机跑比云端快得多，7.2 秒变 1.0 秒。也正因为它只能跑在 Apple Silicon 上，Mac 必须一直开着。 |
| SD 卡 **只做镜像来源**，不靠它开机 | SD 写入的毛病根因没查出来（见下），我们选了让它坏了也不影响开机。 |
| 掉线后 **重启** 而不是热切换 | 把离线状态中途切成在线状态，怎么都改不干净。重启后秒连，更稳。 |

## 硬件：头不动

- **卡住**：资料里写的是 PWM 舵机，照填配置，头根本不动。
- **原因**：这台的头是**总线舵机**。
- **教训**：别假设手上的硬件和资料一模一样。出厂固件是什么版本，最好先记下来，我们当时没记。

## 把 Claude 接进来

- **卡住**：固件只会说 OpenAI 格式的 chat API。
- **做法**：在 VPS 上放一个小服务（shim），把 OpenAI 格式转成 Claude 的请求。后来这台 VPS 一直留在链路里，出门那一步也是靠它。
- **卡住：证书明明对，设备就是报 `-9984`。** VPS 用的是自签证书，设备按裸 IP 连。openssl、curl 都验得过，设备不行。原因是设备的 mbedTLS 2.28 只拿 IP 字符串去比证书里 DNS 类型的名字，不比 IP 类型的。证书里把 IP 再写一遍成 `DNS:` 就过了。签法见 [CERTS.md](CERTS.md)。

## 声音：本地克隆太慢

- **卡住**：本地跑的中文克隆嗓音（Qwen TTS），合成速度 RTF 在 4 到 12 之间，就是说 1 秒的话要算 4 到 12 秒。这种情况下「流式」在数学上就退化成「整段算完再播」，首字延迟只跟字数有关，调度怎么改都没用。
- **当时的办法**：把回复压到 18 个字以内。
- **最后**：换成 MiniMax 云端克隆嗓音，流式，首包约 1.6 秒，跟句子长短无关。18 字的限制就取消了，现在是「一两句，一般 50 字以内」。

## 身体：摸了没反应，摸了八秒才出声

- **卡住 1**：头顶的触摸传感器明明在，摸了就是没反应。原因是反应被 GIF 表情剧场「吃掉」了。
- **卡住 2**：被摸时的台词如果现场用 TTS 合成，首字要 4 到 8 秒，摸一下八秒后才出声，等于坏了。
- **做法**：触摸台词全部**预先合成成 WAV** 存在本地，摸到就直接播，实测不到 0.5 秒。
- **后来**：「被晃就喊要散架」在揣包里走路时一直喊，改成可开关、默认关。

## 延迟：听和播都卡

- **语音识别 7.2 秒 → 1.0 秒**：原来走云端 API，搬回 Mac 本机跑 mlx-whisper。顺带治好了「说的话被识别成乱码、机器人照着乱码回答」。
- **播放一卡一卡**：设备收数据太慢（ESP32 的吞吐大约是 TCP 窗口 ÷ 往返时间）。办法是**开播前先攒一段**（WAV 攒 24 KB）。
- **出门后又卡了**：经海外 VPS 中转，往返时间变长，24 kHz 的 WAV（48 KB/s）又撑不住。改成 **mp3 64 kbps**（8 KB/s），攒 8 KB 就够。
- **踩过的反例**：在播放的读数据函数里加「凑满再返回」的等待，实测把 3.5 秒的音频拖到播了 13 秒。别这么干。
- **摄像头**：一度为了先保语音流畅关掉了。后来改成**按需拍照**：开机不初始化摄像头，只在点右下角拍照按钮时才打开，照片存回 Mac。

## SD 卡

- **卡住**：设备往 SD 卡写文件，大约一半失败（串口 `ff_sd_status(): Check status failed`）。
  - 排除了卡本身：换全新的卡，失败率一模一样；同一张卡在 Mac 上写 60 MB、0 失败。
  - **每次开机就定死一种状态**：20 次开机里一直坏 13 次、一直好 5 次、混合 2 次。所以测失败率必须跨多次开机，单次开机连跑多少轮都只算 1 个样本。
  - SPI 时钟从 25 MHz 降到 10 MHz 没治好；按官方要求补上 `SPI.begin(36,35,37,4)` 之后失败率反而更高，但这一行单独的对照实验没跑成。
  - 那时配置、证书、触摸语音全在 SD 卡上，SD 挂不上就重启，重启还是挂不上，无限循环。那张卡第三次 FAT 报废时，整机就这么变砖了。
- **做法**：查了三天，根因没找到，就**让 SD 退出开机的关键路径**。SD 好的时候，开机顺手把配置、证书、触摸语音镜像进内部存储（SPIFFS）；SD 坏了，就用上次的镜像开机。现在 SD 卡可以一直拔着。
- **顺带踩的坑**：
  - 上游自带的 FTP 写不到 SD 卡（它写的是 SPIFFS），所以另开了几个 HTTP 上传接口。FTP 后来整个关掉了：固定账号密码，能读到存着密钥的配置。
  - SPIFFS 的完整路径最长 31 个字符，GIF 素材名放不下，只好每个场景打包成一个文件。
  - **别把 SPIFFS 换成 LittleFS**：要格式化分区，机器人的人设存在那里，会丢。
- **教训**：别让一个便宜、容易坏的外设成为整台机器开机的单点故障。

## 调试工具本身的坑

这几个让我们误判过好几次「设备崩了」：

- 用 pyserial **打开串口的那一下就会复位 ESP32**，按住 DTR/RTS 也没用。开串口后紧接着连不上，是它在重启，等 10 秒以上。
- **烧录完之后，串口有时只出不进**：日志照常吐，命令一个都收不到。物理拔插一次 USB 才恢复。
- 设备重启后约 90 秒网络才稳。刚烧完就 ping，会误以为改坏了。另外设备本来就不回 ping，真相只在串口里。

## 大脑换成 Claude Code 会话

- **做法**：每轮从最近活跃的 Claude Code 交互窗口 fork 一个分支来回答，答完就丢，不写回原会话。不带工具（见上面「几个关键选择」）。
- **一度以为的坑**：早先看到 fork 的 cache 读取只有约 3.9k tokens，以为每轮都要把整个会话重写一遍。后来连着聊实测才发现，只是隔太久缓存过期了。连着聊每轮读约 195k、写约 8k。

## 出门

想要的是：电脑留在家里，机器人连手机热点，在哪儿都能聊。

- **卡住：回家开机没网，就永远哑着。** 原因是 Wi-Fi 列表只在「上次连的那个连不上」时才登记，正常开机走直连，列表是空的，之后掉线也就没东西可重连。改成开机就登记。
- **掉线恢复用重启**：离线开机后每 20 秒试一次，连上了就直接重启（原因见「几个关键选择」）。
- **卡住：Mac 睡着了隧道就断。** 设成接电永不睡眠。
- **卡住：网关调本机服务间歇失败。** Mac 开着系统代理，本机请求被拽进了代理。在 launchd 里把 `NO_PROXY` 和 `no_proxy` 都设上，大小写两份都要。
- **卡住：流式音频设备播不出来。** 设备不认 HTTP chunked 编码。TTS 服务手写 HTTP，全部按「连接关闭即结束」发。
- **卡住：语音识别收完结果还在等。** 设备那边要读到一个回车符才算结束。网关在识别结果末尾补一个 `\r`。

每一条更细的「症状 / 根因 / 修法 / 怎么验证的」在 [FIELD_NOTES.md](FIELD_NOTES.md)。
